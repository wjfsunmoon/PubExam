## 一、项目介绍话术（按时间递进）

### 30 秒版（电梯演讲）

> 我做了一个全栈的考公智能题库系统叫"考公题目梳理 Agent"。用户粘贴一道公考题目，系统通过 LLM + Prompt 工程自动生成六段式结构化解析——破题眼、正确项分析、干扰项排雷、方法总结、备考提醒。前端用 React + Vite + Tailwind，后端用 Express + Prisma + SQLite，还集成了 JWT 认证。整个项目单端口部署，API 和前端都由 Express 服务。

### 1 分钟版

> 这个项目解决的核心痛点是：考公备考者刷题后缺乏高质量解析，手动整理效率低。我做了一个全栈平台，用户可以粘贴题目，AI 自动生成结构化解析，然后沉淀到题库支持检索和导出。
>
> 技术上，前端 React 18 + Vite + Tailwind CSS，后端 Node.js + Express + Prisma ORM + SQLite。认证用 JWT + bcrypt。最核心的是 AI 解析引擎——我设计了双层 Prompt（System 定义角色和输出格式约束，User 注入题目上下文），调用 OpenAI 兼容 API 生成 JSON 格式的结构化解析。没有 API Key 时自动降级到模板模式，保证流程可走通。部署上，Express 同时服务 API 和构建后的 React 静态文件，实现了单端口部署。

### 3 分钟版（结构化讲述）

> **背景**：考公备考中，刷题后的解析质量直接决定提分效率。市面上的题库 App 解析参差不齐，且无法个性化沉淀。
>
> **目标**：做一个能自动生成高质量结构化解析的全栈题库系统。
>
> **架构设计**：
> - 前端 React 18 + Vite 构建，Tailwind CSS 做样式，React Router 管理路由，Axios 封装 HTTP 请求
> - 后端 Express 提供 RESTful API，Prisma ORM 操作 SQLite 数据库
> - 认证层 JWT + bcrypt，实现注册/登录/请求鉴权
> - AI 引擎通过双层 Prompt 设计调用 LLM，生成 JSON 格式的结构化解析
>
> **核心难点与解决**：
> 1. **AI 输出的结构化保障**：LLM 输出不稳定，我用 System Prompt 约束输出 JSON 格式，设 temperature=0.3 降低随机性，还做了 JSON 解析容错——清洗 markdown 代码块包裹，解析失败时保底返回原始文本
> 2. **无 API Key 的降级策略**：设计了模板模式，无 Key 时自动生成框架结构，标注"待 AI 生成"，保证 Demo 可演示
> 3. **单端口部署**：Express 用 express.static 服务构建后的 React 文件，加 SPA fallback 处理客户端路由，一个端口同时跑 API 和前端
>
> **结果**：完整的全栈应用，支持用户注册登录、题目录入、AI 解析生成、题库管理、数据看板、Markdown/JSON 导出。预置了一道完整的行测判断推理削弱型示例题。

## 二、架构设计类问题

### Q1：请介绍一下你的项目架构

**回答话术：**

> 这是一个经典的三层架构：前端展示层 → 后端 API 层 → 数据存储层。
>
> 前端是 React SPA，用 Vite 构建，Tailwind 做样式。通过 Axios 调用后端 API，请求拦截器自动注入 JWT。
>
> 后端是 Express，采用中间件管道模式。请求进来先过 CORS 和 JSON 解析，然后路由分发到三个模块：认证（/api/auth）、题目管理（/api/questions）、AI 解析（/api/analysis）。每个受保护的路由前面挂 JWT 鉴权中间件。
>
> 数据层是 SQLite + Prisma ORM。Prisma 提供类型安全的查询 API，还管理数据库迁移。两张表：User 和 Question，一对多关系，级联删除。
>
> 部署上，Express 既服务 API，又通过 express.static 服务构建后的 React 静态文件，加上 SPA fallback 处理客户端路由，实现单端口部署。

### Q2：为什么选 React + Express + Prisma 这个技术栈？

**回答话术：**

> **React**：生态最成熟，组件化开发模式清晰，Hooks 让函数组件也能管理状态和副作用。选 Vite 是因为它是 ESM 原生构建，比 Webpack 快 10-100 倍。
>
> **Express**：Node.js 最轻量的 HTTP 框架，中间件机制灵活，适合中小型项目。如果用 NestJS 对于这个体量是过度设计。
>
> **Prisma**：相比手写 SQL，它提供类型安全的查询 API，Schema 即文档，自动生成迁移文件，开发效率高。相比 Sequelize，Prisma 的 Schema 定义更直观，类型推断更好。
>
> **SQLite**：零配置，文件级数据库，不需要额外安装数据库服务。对于个人项目和 Demo 足够。如果上线生产环境，Prisma 改一行 datasource 配置就能切换到 PostgreSQL。

### Q3：为什么用 SQLite 而不是 MySQL/PostgreSQL？

**回答话术：**

> 这是基于项目阶段的权衡。当前是个人项目/Demo 阶段，SQLite 零配置、文件级、不需要独立数据库进程，部署成本最低。
>
> 但架构上没有锁死在 SQLite——Prisma ORM 封装了数据库操作，切换数据库只需要改 `schema.prisma` 中的 datasource provider 和连接字符串，业务代码完全不用改。这是 ORM 的核心价值之一：数据库可移植性。
>
> 如果上生产，我会切到 PostgreSQL，因为：①支持原生 JSON 类型（现在 tags/options 存为字符串需要 JSON.parse）；②支持并发写入（SQLite 是文件锁）；③有更完善的权限管理和备份方案。

### Q4：为什么用 JWT 而不是 Session + Cookie？

**回答话术：**

> 两个核心原因：
>
> 1. **无状态**：JWT 把用户信息编码在 token 里，服务器不需要存储 session。水平扩展时不需要共享 session 存储（Redis）。而 Session 需要服务器端存储，多实例部署时要处理 session 共享问题。
>
> 2. **前后端分离友好**：JWT 放在 Authorization 头里，不依赖 Cookie 机制，天然适配跨域场景。如果后续做移动端 App，JWT 也直接可用。
>
> 当然 JWT 也有缺点：签发后无法主动失效（除非维护黑名单），不适合需要强制登出的场景。我这个项目用 7 天过期 + 前端 401 拦截自动跳转登录来处理过期。

### Q5：你的 API 是怎么设计的？遵循了什么规范？

**回答话术：**

> 我遵循 RESTful 风格设计 API：
>
> | 方法 | 路径 | 语义 |
> |------|------|------|
> | POST | /api/auth/register | 注册 |
> | POST | /api/auth/login | 登录 |
> | GET | /api/questions | 列表（支持分页、筛选） |
> | GET | /api/questions/:id | 详情 |
> | POST | /api/questions | 创建 |
> | PUT | /api/questions/:id | 更新 |
> | DELETE | /api/questions/:id | 删除 |
> | GET | /api/questions/stats/summary | 统计 |
> | POST | /api/analysis/generate | AI解析 |
>
> 设计要点：
> - 用 HTTP 方法表达操作语义（GET 查、POST 增、PUT 改、DELETE 删）
> - 用 HTTP 状态码表达结果（201 创建成功、404 不存在、401 未认证、409 冲突）
> - 统一响应格式：列表返回 `{ items, total, page, totalPages }`，错误返回 `{ error: "消息" }`
> - 需要鉴权的路由统一挂 JWT 中间件

## 三、数据库类问题

### Q6：你的数据库表是怎么设计的？

**回答话术：**

> 两张表：User 和 Question，一对多关系。
>
> User 表：id、username（唯一）、password（bcrypt 哈希）、createdAt。
>
> Question 表比较丰富，分三组字段：
> - 元数据组：module、submodule、questionType、difficulty、tags、frequency、year
> - 内容组：stem（题干）、options（JSON 字符串）、correctAnswer
> - 解析组：breakthrough、correctAnalysis、trapAnalysis、methodSummary、examTips
> - AI 元数据：analysisSource（ai/manual/template）、aiModel
>
> 关系上设了 `onDelete: Cascade`，用户删除时题目自动级联删除。索引上对 userId 和 `[module, submodule]` 建了联合索引，优化查询性能。

### Q7：tags 为什么不建独立表？这样设计有什么优缺点？

**回答话术：**

> 这是权衡决策。建独立 Tag 表需要三表关联（Question-QuestionTag-Tag），查询时要 JOIN，写入时要维护关联关系。对于当前场景——标签数量少（每题 2-4 个）、不需要按标签反查——直接用 JSON 字符串存储更简单。
>
> 优点：简单，无 JOIN 开销，代码清晰。
> 缺点：不能按标签做高效检索（要用 LIKE 或 JSON 函数），标签不能去重管理。
>
> 如果需求演进到需要标签云、按标签筛选统计，就应该拆成独立表。这就是"用空间换复杂度"还是"用复杂度换空间"的权衡。

### Q8：Prisma ORM 相比手写 SQL 有什么优缺点？

**回答话术：**

> **优点：**
> 1. 类型安全：Prisma Client 根据 Schema 自动生成类型，编译期就能发现字段名拼写错误
> 2. Schema 即文档：`schema.prisma` 文件就是数据库设计的单一真相来源
> 3. 迁移自动化：`prisma migrate dev` 自动生成迁移文件，版本化管理 schema 变更
> 4. 防注入：参数化查询，天然防 SQL 注入
> 5. 数据库可移植：改 datasource 即可切换数据库引擎
>
> **缺点：**
> 1. 有性能开销：ORM 生成的 SQL 不一定最优，复杂查询可能不如手写 SQL 高效
> 2. 学习曲线：需要学 Prisma 的 Schema 语法和查询 API
> 3. 包体积：Prisma Client 和引擎有一定体积
>
> 对于这个项目，开发效率和类型安全的价值远大于性能开销。

### Q9：什么是数据库迁移？为什么要做迁移？

**回答话术：**

> 迁移是数据库 schema 的版本控制。每次修改表结构（加字段、改类型、建表），Prisma 生成一个迁移文件，里面记录了对应的 SQL DDL 语句。
>
> **为什么要做？**
> 1. 团队协作：别人 clone 项目后，跑一遍迁移就能创建出相同的表结构
> 2. 版本回溯：如果某次 schema 变更出问题，可以回退到上一个迁移版本
> 3. 生产部署：上线时执行迁移，安全地更新数据库结构而不丢数据
>
> 在这个项目中，`prisma/migrations/` 目录下的 `20260919063610_init/migration.sql` 就是初始建表迁移。

### Q10：如何防止 SQL 注入？

**回答话术：**

> 用 Prisma ORM 天然防注入。Prisma 底层用的是参数化查询（Prepared Statement），用户输入不会被拼接到 SQL 字符串中，而是作为参数传递。
>
> 比如 `prisma.question.findMany({ where: { stem: { contains: userInput } } })`，Prisma 会生成 `WHERE stem LIKE ?` 然后把 userInput 作为参数传入，即使用户输入 `' OR 1=1 --` 也不会被当作 SQL 执行。
>
> 如果用手写 SQL 就必须自己做参数化，绝不能字符串拼接。

## 四、后端类问题

### Q11：Express 中间件是什么？执行顺序是怎样的？

**回答话术：**

> 中间件是 Express 的核心设计——一个函数 `(req, res, next) => {}`，请求依次穿过每个中间件，像流水线一样。
>
> 每个中间件可以：
> - 修改 req/res 对象
> - 结束请求-响应循环（直接 res.send()）
> - 调用 next() 将控制权交给下一个中间件
>
> 执行顺序就是注册顺序。我的项目中：
> ```
> cors() → express.json() → API路由 → API 404 → express.static → SPA fallback → 错误处理
> ```
>
> 特别注意：错误处理中间件必须 4 个参数 `(err, req, res, next)`，Express 通过参数数量识别它，放在最后。

### Q12：JWT 的原理是什么？

**回答话术：**

> JWT（JSON Web Token）是一种无状态的认证方案。它由三部分组成，用点号分隔：
>
> 1. **Header**：声明算法（HS256）和 token 类型（JWT）
> 2. **Payload**：存放业务数据（我放的是 userId），还有标准声明 iat（签发时间）和 exp（过期时间）
> 3. **Signature**：用 Header + Payload + 密钥做 HMAC 签名
>
> 前两部分是 Base64 编码（不是加密，可以解码），第三部分是签名。
>
> **认证流程**：服务端签发 token → 客户端存储 → 每次请求带上 → 服务端用密钥验签 → 验证通过则信任 Payload 中的 userId。
>
> **安全要点**：密钥必须保密，泄露后任何人都能伪造 token。Payload 不要放敏感信息（因为可以解码）。

### Q13：bcrypt 加密的原理？为什么不用 MD5？

**回答话术：**

> **为什么不用 MD5**：MD5 是哈希算法，设计目标是快。但密码存储恰恰需要"慢"——攻击者拿到哈希后可以快速穷举破解。而且 MD5 不加盐的话，相同密码哈希值相同，容易被彩虹表攻击。
>
> **bcrypt 的优势**：
> 1. **加盐**：自动生成随机盐值混入密码再哈希，相同密码生成不同哈希，防彩虹表
> 2. **慢哈希**：bcrypt 设计上就是慢的（通过 cost factor 控制计算轮数），增加暴力破解成本
> 3. **cost 可调**：`bcrypt.hash(password, 10)` 中的 10 是 cost factor，硬件升级后可以调大增加计算量
>
> 我用的是 10 轮，这是比较标准的值，单次哈希约 100ms，安全性和性能的平衡点。

### Q14：CORS 是什么？为什么要配置？

**回答话术：**

> CORS（Cross-Origin Resource Sharing）是浏览器的同源策略安全机制。当前端（localhost:5173）请求不同源的后端（localhost:3001）时，浏览器会阻止响应——除非后端在响应头中明确允许。
>
> `cors()` 中间件会自动添加 `Access-Control-Allow-Origin: *` 等响应头，告诉浏览器允许跨域访问。
>
> 生产环境应该限制为具体域名而不是 `*`，避免任意来源访问。

### Q15：你的 API 如何做参数校验？

**回答话术：**

> 当前是在路由处理器中做基础校验，比如检查 username/password 是否为空、长度范围、密码最少 6 位。
>
> 如果要更规范，可以用 Zod 或 Joi 做声明式校验——定义一个 schema，中间件自动校验请求体，不通过直接返回 400。这是我后续可以改进的点。

### Q16：你是怎么处理错误的？

**回答话术：**

> 分两层：
>
> 1. **路由层**：每个路由处理器用 try-catch 包裹，捕获错误后调用 next(err) 或直接返回对应状态码（400 参数错误、404 不存在、409 冲突、401 未认证）
>
> 2. **全局错误处理中间件**：放在最后，4 参数函数 `(err, req, res, next)`，捕获所有未处理的错误，返回 500 + 统一错误格式 `{ error: "消息" }`
>
> 这样保证任何异常都不会暴露堆栈信息给客户端，也不会让服务崩溃。

## 五、前端类问题

### Q17：React 的虚拟 DOM 是什么？有什么好处？

**回答话术：**

> 虚拟 DOM 是一个 JavaScript 对象树，是真实 DOM 的轻量级映射。React 每次状态变更后生成新的虚拟 DOM 树，与前一棵做 diff，计算出最小变更集，然后批量更新真实 DOM。
>
> 好处：
> 1. **性能**：直接操作真实 DOM 是昂贵的（会引起重排重绘），虚拟 DOM 把多次状态变更合并为一次 DOM 更新
> 2. **跨平台**：虚拟 DOM 是 JS 对象，不依赖浏览器环境，React Native 就是基于虚拟 DOM 渲染原生组件
> 3. **声明式**：开发者只需描述"UI 应该长什么样"，不用关心怎么操作 DOM

### Q18：useState 和 useEffect 的作用？在你的项目中怎么用的？

**回答话术：**

> **useState**：管理组件内部状态。状态变更触发重新渲染。比如 QuestionBank 中用 `useState` 管理 `items`（题目列表）、`filters`（筛选条件）、`loading`（加载状态）。
>
> **useEffect**：处理副作用——组件挂载后、依赖项变更时执行的操作。比如 Dashboard 中 `useEffect(() => { questionApi.stats().then(...) }, [])` 在组件挂载时拉取统计数据，空数组表示只执行一次。
>
> QuestionBank 中我用 useEffect 监听 filters 变化，自动重新拉取题目列表。

### Q19：React Router 是怎么实现路由的？BrowserRouter 和 HashRouter 的区别？

**回答话术：**

> React Router 在客户端拦截 URL 变化，根据路径匹配对应组件渲染，不向服务器发请求（除了首次加载）。
>
> **BrowserRouter**：使用 HTML5 History API（pushState），URL 是正常的路径如 `/bank`。但直接访问或刷新时浏览器会向服务器请求这个路径，所以服务器必须配置 fallback 返回 index.html。我在 Express 中用 `app.get('*')` 做了这个 fallback。
>
> **HashRouter**：URL 中带 `#`，如 `/#/bank`。hash 变化不会触发服务器请求，不需要服务器配置。但 URL 不太美观，SEO 不友好。
>
> 我选了 BrowserRouter 因为 URL 更规范，配合 Express SPA fallback 完美工作。

### Q20：为什么用 Context API 而不是 Redux？

**回答话术：**

> 核心判断标准是**状态复杂度**。我的全局状态只有 `user`（当前登录用户）和 `loading`（初始化状态），涉及 2 个字段、3 个操作函数。
>
> Redux 引入 action、reducer、store、middleware 四层概念，对于这种简单状态是过度设计。Context + useState 三行代码就能解决跨组件状态共享。
>
> 如果状态复杂——比如有多个异步数据流、状态间有复杂依赖、需要时间旅行调试——那就该用 Redux 或 Zustand。

### Q21：Axios 拦截器是干什么的？

**回答话术：**

> 拦截器是 Axios 的核心特性，可以在每个请求发出前和响应返回后统一处理逻辑。
>
> **请求拦截器**：我用来从 localStorage 取 JWT token，自动注入到 Authorization 头。这样每个 API 调用不用手动加 token。
>
> **响应拦截器**：我用来检查 401 状态码——如果收到 401 说明 token 过期，自动清除本地 token 并跳转登录页。非 401 错误正常抛出由调用方处理。
>
> 好处是认证逻辑集中在一处，DRY（Don't Repeat Yourself）。

### Q22：Tailwind CSS 的优缺点？

**回答话术：**

> **优点：**
> 1. 开发效率高：不用想类名，直接写 `bg-brand-600 text-white rounded-lg`
> 2. 包体积小：Tree-shaking 只打包用到的类，最终 CSS 约 20KB（gzip 4KB）
> 3. 一致性好：设计系统内建在配置中（颜色、间距、字号），不会出现 #f0f0f0 和 #f5f5f5 混用
>
> **缺点：**
> 1. HTML 中类名很长，可读性降低
> 2. 学习曲线：需要记忆大量类名
> 3. 复杂动画和伪类不如 Sass 灵活
>
> 但对于中后台应用和个人项目，开发效率的优势远大于可读性的劣势。

### Q23：SPA（单页应用）的原理是什么？

**回答话术：**

> SPA 的核心是：只加载一次 HTML，后续所有"页面切换"都是 JavaScript 在客户端操作 DOM 完成的。
>
> 首次访问时，服务器返回 index.html + JS bundle。之后用户点击导航链接，React Router 拦截 URL 变化，卸载旧组件渲染新组件，不发 HTTP 请求。
>
> 好处：切换流畅（无白屏）、减少服务器请求。
> 挑战：首屏加载慢（要下载整个 JS bundle）、SEO 不友好（爬虫看到的是空壳 HTML）。
>
> 我的 Express 配了 SPA fallback：`app.get('*', (req, res) => res.sendFile('index.html'))`，确保用户直接访问 `/login` 或 `/bank` 时也能正确返回 index.html。

## 六、安全类问题

### Q24：JWT 存在哪里？有什么安全风险？

**回答话术：**

> 我存的是 localStorage。
>
> **风险**：localStorage 可以被 JavaScript 读取，如果页面有 XSS 漏洞，攻击者可以偷走 token。
>
> **更安全的方案**是 httpOnly Cookie：设置 httpOnly 标志后 JavaScript 无法读取，防 XSS 偷取。但 Cookie 方案需要处理 CSRF（跨站请求伪造），可以通过 SameSite 属性缓解。
>
> 我选 localStorage 是因为前后端分离架构下实现简单，且当前项目没有高敏感数据。如果上线生产，应该切到 httpOnly Cookie + CSRF Token 方案。

### Q25：如何防止 XSS 和 CSRF？

**回答话术：**

> **XSS（跨站脚本攻击）**：攻击者注入恶意脚本到页面中。
> - 防御：React 默认转义 JSX 中的变量（`{userInput}` 会被 HTML 转义），不使用 dangerouslySetInnerHTML
> - 我渲染 Markdown 用的是 react-markdown，它内部做了转义处理，不会直接插入 HTML
>
> **CSRF（跨站请求伪造）**：攻击者诱导用户在已登录状态下发送恶意请求。
> - 防御：JWT 方案天然防 CSRF（token 在 Authorization 头中，不是自动携带的 Cookie）。如果是 Cookie 方案则需要 CSRF Token + SameSite 属性

### Q26：你的密码是怎么存储的？

**回答话术：**

> 密码绝对不会明文存储。流程是：
> 1. 注册时：`bcrypt.hash(password, 10)` —— 加盐 10 轮哈希后存入数据库
> 2. 登录时：`bcrypt.compare(password, user.password)` —— 比较明文和哈希
>
> bcrypt 的哈希是单向不可逆的，数据库泄露后攻击者也无法还原明文密码。而且每个密码的盐是随机的，相同密码生成不同哈希，防彩虹表攻击。

## 七、AI/Prompt 工程类问题

### Q27：你是怎么集成 LLM 的？

**回答话术：**

> 我封装了一个 AI 服务层（ai.js），调用 OpenAI 兼容的 Chat Completions API。架构是：
>
> 1. **检查配置**：读取环境变量 OPENAI_API_KEY，判断是 AI 模式还是模板模式
> 2. **构建 Prompt**：System Prompt 定义角色和输出格式，User Prompt 注入题目上下文
> 3. **调用 API**：POST /chat/completions，设 temperature=0.3 降低随机性
> 4. **解析响应**：从 LLM 返回的文本中提取 JSON，做容错处理
> 5. **返回结果**：附加 analysisSource 和 aiModel 元数据
>
> 这层封装的好处是：业务路由不关心 AI 实现细节，只调 `analyzeQuestion(data)` 拿结果。

### Q28：Prompt 工程是什么？你是怎么设计的？

**回答话术：**

> Prompt 工程是设计 LLM 输入提示词以获得稳定、可控输出的技术。
>
> 我设计了**双层 Prompt**：
>
> **System Prompt（不变层）**：
> - 定义角色："拥有10年以上国考/省考命题研究与教学经验的资深公考教研专家"
> - 定义红线："禁止编造""政治中立""拒绝模糊""时效敏感"
> - 定义输出格式：严格的 JSON schema，每个字段的含义和类型
>
> **User Prompt（变化层）**：
> - 注入题目元数据（模块、题型、难度）
> - 注入题干、选项、正确答案
>
> **关键技巧**：
> 1. **角色扮演**：给 LLM 一个明确身份，输出质量显著提升
> 2. **输出约束**：明确要求输出 JSON，禁止输出其他内容
> 3. **示例引导**：JSON schema 本身就是格式示例
> 4. **温度控制**：temperature=0.3，偏低确保输出稳定可解析

### Q29：没有 API Key 时怎么办？

**回答话术：**

> 我设计了**降级策略**——模板模式。没有 API Key 时，`analyzeQuestion()` 不调用 LLM，而是走 `generateTemplateAnalysis()` 生成一个基础框架：
>
> - breakthrough 标注"[待 AI 生成]"
> - trapAnalysis 为每个错误选项生成占位条目，errorType 标注"待分析"
> - analysisSource 标记为 "template"
>
> 这样保证：没有 API Key 也能演示完整流程，用户录入题目后看到的是结构化框架而非报错。配置 Key 后自动切换到真实 AI 解析。
>
> 这是**优雅降级**的设计思想——核心功能可用，增强功能按需开启。

### Q30：LLM 返回的 JSON 不标准怎么办？

**回答话术：**

> 这是实际开发中的常见问题。LLM 可能在 JSON 外面包裹 markdown 代码块（```json ... ```），或者在 JSON 前后加解释文字。
>
> 我的处理策略：
> 1. **清洗**：用正则去掉 ```json 和 ``` 标记
> 2. **尝试解析**：JSON.parse()
> 3. **容错**：如果解析失败，不抛错，而是把原始文本作为 correctAnalysis 返回，breakthrough 标注"[解析格式异常]"
>
> 这样即使 LLM 输出格式异常，也不会导致接口 500 错误，用户至少能看到原始内容。

## 八、性能与优化类

### Q31：如何优化前端性能？

**回答话术：**

> 当前项目已有的优化：
> 1. **Vite 构建**：ESM 原生按需加载，开发时秒级热更新；生产构建 Tree-shaking，最终 JS 约 130KB（gzip）
> 2. **Tailwind Tree-shaking**：只打包用到的 CSS 类，最终 20KB（gzip 4KB）
> 3. **防抖搜索**：QuestionBank 的关键词搜索用了 300ms 防抖，避免每次按键都发请求
>
> 可以进一步优化的方向：
> 1. **代码分割**：用 React.lazy + Suspense 按路由懒加载，减小首屏 bundle
> 2. **API 缓存**：用 React Query 做请求缓存，避免重复请求
> 3. **虚拟列表**：题库列表数据量大时用 react-window 虚拟滚动

### Q32：数据库查询如何优化？

**回答话术：**

> 当前已做的：
> 1. **索引**：对 userId 和 [module, submodule] 建了索引，WHERE 条件和排序走索引
> 2. **分页**：列表接口支持 page/pageSize，避免一次查全表
> 3. **并行查询**：列表接口用 Promise.all 同时查数据和 count，而不是串行
>
> 可以进一步优化的：
> 1. 如果数据量大，SQLite 文件锁会成为瓶颈，应切到 PostgreSQL
> 2. 题干搜索现在用 LIKE contains，大数据量应该用全文索引
> 3. 统计接口的 groupBy 在数据量大时可以加缓存

### Q33：如果用户量大了怎么办？

**回答话术：**

> 这涉及从单机到分布式的演进：
>
> 1. **数据库**：SQLite → PostgreSQL/MySQL，支持并发写入
> 2. **缓存层**：加 Redis 缓存热点数据和统计结果
> 3. **服务拆分**：Express 单体 → 微服务，AI 解析、题库管理拆成独立服务
> 4. **负载均衡**：Nginx 反向代理 + 多实例 Express，JWT 无状态天然支持水平扩展
> 5. **文件存储**：SQLite 文件级 → 对象存储（S3/OSS）存题目附件
> 6. **消息队列**：AI 解析耗时长，可以改成异步——请求入队列，完成后通知前端

## 九、设计决策与权衡

### Q34：项目中遇到的最大难点是什么？

**回答话术：**

> 最大的难点是**AI 输出的结构化保障**。
>
> LLM 的输出本质上是自由文本，不可控。但我的系统需要把解析结果存入数据库的结构化字段（breakthrough、trapAnalysis 等），前端要按固定结构渲染。

>
> 最终效果：大多数情况下能正确解析出 JSON，异常情况下也不会崩溃。

### Q36：你的项目有什么亮点？

**回答话术：**

## 十、可能追问的问题

### Q37：JWT 如何实现主动失效（强制登出）？

> JWT 签发后无法主动失效，因为验证只靠密钥验签。要实现强制登出可以：
> 1. **Token 黑名单**：在 Redis 中存失效的 token，每次验证时查一下
> 2. **短期 Token + Refresh Token**：Access Token 15分钟过期，Refresh Token 7天，用 Refresh 换新的 Access
> 3. **版本号机制**：User 表加 tokenVersion 字段，改密码时 +1，JWT 中带 version，验证时比对

### Q38：如果 LLM 返回的解析质量不好怎么办？

> 1. **Prompt 迭代**：根据 bad case 调整 System Prompt，增加 few-shot examples
> 2. **人工审核**：analysisSource 区分 ai/manual，用户可手动修改后覆盖
> 3. **模型选择**：不同难度题目路由到不同模型（简单题用便宜模型，难题用强模型）
> 4. **多轮生成**：生成后让另一个 LLM 评审打分，低于阈值重新生成

### Q39：你的项目如何做 CI/CD？

> 可以用 GitHub Actions：
> ```yaml
> # .github/workflows/ci.yml
> on: [push, pull_request]
> jobs:
>   test:
>     runs-on: ubuntu-latest
>     steps:
>       - uses: actions/checkout@v4
>       - uses: actions/setup-node@v4
>       - run: npm ci
>       - run: npm test
>       - run: npm run build
> ```
> 部署到服务器时：拉代码 → npm install → prisma migrate → vite build → pm2 start

### Q40：为什么 Express 用 app.get('*') 做 SPA fallback 而不是用中间件？

> 因为 `app.get('*')` 只拦截 GET 请求。如果是 `app.use()` 会拦截所有方法（包括 POST/PUT/DELETE），但这些 API 请求应该被前面的 API 路由处理。用 `app.get('*')` 确保只有非 API 的 GET 请求才走 SPA fallback，不影响 API 路由。
